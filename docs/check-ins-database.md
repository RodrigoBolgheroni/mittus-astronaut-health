# Daily check-in data specification

**Status:** synchronized with the inspected Supabase schema; executable SQL lives in `supabase/migrations`.
**Database:** PostgreSQL (Supabase)
**Purpose:** Store one health check-in per day and demo session, so records can be queried on a calendar and used to populate indicator history.

Table, column, and technical value names are in English. Data used in the demo is simulated.

## Current model

Table: `check_ins`

| Column | PostgreSQL type | Required | Description |
| --- | --- | --- | --- |
| `id` | `uuid` | Yes | Unique record identifier, generated by the database. |
| `session_id` | `uuid` | Yes | Identifier of the demo session that owns the record. |
| `check_in_date` | `date` | Yes | Reference date of the check-in, without a time. |
| `sleep_hours` | `numeric(4,2)` | Yes | Reported sleep duration, from 0 to 24 hours; decimal values are accepted. |
| `stress_level` | `smallint` | Yes | Stress level, from 1 to 5. |
| `mood_level` | `smallint` | Yes | Emotional state, from 1 to 5. |
| `team_conflict_level` | `smallint` | Yes | Team conflict level, from 1 to 5. |
| `fatigue` | `smallint` | Yes | Fatigue level, from 1 to 7. |
| `description` | `text` | No | Optional free-text description, limited to 2,000 characters by the API. |
| `created_at` | `timestamptz` | Yes | Time when the record was created. |
| `updated_at` | `timestamptz` | Yes | Time of the last change; updated by the backend. |

`sleep_hours` uses decimal hours: `7.50` means 7 hours and 30 minutes. The database and API enforce a range of 0–24 and a precision of two decimal places.

### Mood and stress scales

Each dimension is recorded independently using whole numbers from 1 to 5. Values 2, 3, and 4 represent intermediate points between the extremes.

| Column | Value 1 | Value 5 |
| --- | --- | --- |
| `stress_level` | Very calm | Very stressed |
| `mood_level` | Very happy / positive | Very sad / negative |
| `team_conflict_level` | No team conflict | High team conflict |

For each dimension, higher values represent more stress, a more negative emotional state, or more conflict, respectively.

### Fatigue scale

| Value | Interface description |
| --- | --- |
| 1 | Fully alert and wide awake |
| 2 | Very active and responsive, but not at peak alertness |
| 3 | Feeling well and ready |
| 4 | A little tired and less energetic |
| 5 | Moderately tired and fatigued |
| 6 | Extremely tired, with great difficulty concentrating |
| 7 | Completely exhausted and unable to function effectively |

## Integrity and access rules

- There is **at most one record per `session_id` and `check_in_date`**. A new write for the same combination updates the existing record.
- All indicators are required in a complete check-in. Database constraints also prevent values outside the defined scales.
- The backend identifies the session from its server-issued cookie. The client cannot choose the record's `session_id`; all reads and changes must be scoped to the identified session.
- This proposal does not create a session table or a foreign key for `session_id`. Session issuance and persistence must be defined during implementation; a relationship can be added if a session table is introduced.
- `check_in_date` is a calendar date, not an instant. **UTC is the proposed** basis for determining the current date; the mission timezone still needs confirmation.
- Whether check-ins for past dates may be created or changed remains undecided and must be enforced by the backend after a product decision.
- `created_at` and `updated_at` represent instants. In this proposal, the backend updates `updated_at` after each change; the database does not update it automatically.

## Example operations

### Create or update a check-in

The positional values are parameters supplied by the backend; `$1` is the session identifier obtained on the server.
```sql
INSERT INTO check_ins (
    session_id, check_in_date, sleep_hours, stress_level,
    mood_level, team_conflict_level, fatigue
)
VALUES ($1, $2, $3, $4, $5, $6, $7)
ON CONFLICT (session_id, check_in_date)
DO UPDATE SET
    sleep_hours = EXCLUDED.sleep_hours,
    stress_level = EXCLUDED.stress_level,
    mood_level = EXCLUDED.mood_level,
    team_conflict_level = EXCLUDED.team_conflict_level,
    fatigue = EXCLUDED.fatigue,
    updated_at = now()
RETURNING *;
```

### Query a calendar month

Use a range with an inclusive start and exclusive end. For November 2026, for example, `$2` is `2026-11-01` and `$3` is `2026-12-01`.

```sql
SELECT check_in_date, sleep_hours, stress_level, mood_level,
       team_conflict_level, fatigue
FROM check_ins
WHERE session_id = $1
  AND check_in_date >= $2
  AND check_in_date < $3
ORDER BY check_in_date;
```

Days without records are absent from the result; the interface can display them as days without a check-in.

## Confirmed implementation decisions

- All numeric indicators are required; only `description` is optional.
- The server uses UTC and accepts writes only for the current date.
- Signed anonymous demo cookies last 30 days; every health query filters by the validated session.
- Mission tables are mapped without adding a mandatory mission relationship to check-ins.
- The [API specification](specs/check-ins-spec.md) and [backend README](../backend/README.md) describe the implemented contracts and isolated migration replay.
